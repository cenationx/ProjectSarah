# Project Sarah: Findings Report

## Findings

### 1. [Severity: High] Follow retargeting forces unconditional action queue wipe
- **Location:** `Commands.lua` line 646, `Engine.lua` line 326.
- **Failure Scenario:** A mid-stride `Follow` retargeting invokes `adapter.stop()`, which unconditionally executes `ISTimedActionQueue.clear(npc)`. If any lightweight actions (e.g., shouting, reloading) are queued concurrently by future systems or other mods, they are obliterated every few ticks when Sarah updates her path to the moving player.
- **Evidence:** Verified by code reading. `adapter.stop` calls `queue.clear`.
- **Confidence:** High.
- **Smallest fix:** Limit `adapter.stop()` to canceling only the `SarahWalkAction` (or its specific pathing), or allow the queue to handle the override natively without blanket wiping.

### 2. [Severity: High] Skipped base cleanup for retired walk actions
- **Location:** `Engine.lua` lines 110-127 (`perform`) and 128-147 (`stop`).
- **Failure Scenario:** `adapter.stop()` increments `actionToken` before calling `ISTimedActionQueue.clear`. When `clear` subsequently calls `stop()` on the current `SarahWalkAction`, `isCurrentOwner()` returns `false`. This causes the action to skip calling `ISWalkToTimedAction.stop(self)`, missing native engine teardowns (like `self.character:StopAllActionQueue()` and animation halts).
- **Evidence:** Verified by code reading. Base calls are gated behind `if isOwner`.
- **Confidence:** High.
- **Smallest fix:** Move `ISWalkToTimedAction.stop(self)` and `perform(self)` outside the `isOwner` block so native lifecycle completes regardless of internal logical ownership.

### 3. [Severity: Medium] Observation memory fail-closed wipes on unverified pause state
- **Location:** `Console.lua` lines 158-167.
- **Failure Scenario:** If the Kahlua bridge for `GameTime.isGamePaused` or `UIManager.getSpeedControls` behaves unexpectedly (e.g., throwing due to a missing method signature), `pauseVerified` remains false. This triggers `resetKnowledge()` on every tick, effectively permanently blinding the NPC's observation memory.
- **Evidence:** Verified by code reading.
- **Confidence:** Medium (depends on actual B42.21 Kahlua exposure rules).
- **Smallest fix:** Write a native diagnostic hook to log the presence and type of these specific getters before relying on them to drive memory clearing.

### 4. [Severity: Low/Architectural] LightSourceSnapshot is overly complex and inert
- **Location:** `LightSourceSnapshot.lua`.
- **Failure Scenario:** 861 lines of defensive indexing and power semantics testing, but zero native bindings. Its complexity currently poses no direct risk because it's completely unused, but it bloats the codebase before foundational milestones (M1) are natively verified.
- **Evidence:** Grep confirms no usages outside tests and documentation.
- **Confidence:** High.
- **Smallest fix:** Keep it inert until M1 is proven in-engine. Do not wire it up yet.

## Roadmap Assessment & Next Actions
The roadmap explicitly holds on external model AI and independent lighting until the native movement foundation is proven. M1 (Follow and Stop) implementation is present but its interaction with `ISTimedActionQueue` is aggressive and risky. The test suite (`tools/test_*.py`) heavily relies on Python mocks that perfectly mimic the Lua adapter's expectations rather than realistic Java/Kahlua bridge failures. Passing offline tests do not establish native engine acceptance here.

### Highest-Value Next Actions:
1. **Fix `SarahWalkAction` Base Teardown:** Move base class method calls outside the `isOwner` check to prevent dangling native states.
2. **Refine Follow Retargeting:** Remove `ISTimedActionQueue.clear(npc)` from `adapter.stop()`; investigate canceling just the active path or using native action interruption rather than nuking the queue.
3. **Conduct In-Game M1 Validation:** Deploy the current code to the isolated profile and run an explicit, verified native gameplay test on the Follow/Stop retargeting loop before advancing perception or lighting logic.
